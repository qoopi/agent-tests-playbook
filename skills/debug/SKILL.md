# debug

From a red run to a cause, ending in `debug.md` in the shape of `${CLAUDE_PLUGIN_ROOT}/templates/handoffs/debug.md`. Cause classes, what a fix may change and the entry format: `${CLAUDE_PLUGIN_ROOT}/rules/debugging.md`. Redact before quoting: trace entries carry cookies and headers, accounts are named by variable.

## Steps

1. **Reproduce.** From a CI artifact, read attempt one's trace, not the retry's, and note the commit, the runner and the attempt; `gh run list --workflow <file> --branch <branch> --json conclusion,headSha` gives the rerun history. Locally, `test_run` on the one spec, then determinism: `bunx playwright test <spec> --grep "<title>" --repeat-each 10 --retries 0 --workers 1`. Ten of ten red is deterministic. Green alone means the suite at the configured workers next; green there too means more repeats and the spec beside the other specs of its area. Cut steps one at a time until every remaining step is load-bearing. Done when a loop reproduces the reported symptom, or the entry says no loop with what was tried and which artifact would help.

2. **Observe.** `test_debug` on the test pauses it at the failing step with the page live: `browser_snapshot`, `browser_console_messages`, `browser_network_requests`, and `browser_generate_locator` on the intended element. Read the whole error, then the trace's failing action, console and network. Compare with a passing test on the same page and list every difference. `git log -p` on the spec, its page object and the config since the last green. When CI is red and local green, tabulate the differences first: environment and base URL, browser build, workers, viewport, account, time of day. Done when the observations are written.

3. **Classify.** Two independent markers, worked in the order product, test, environment, data, stopping at the first the evidence supports. Product: a page error at the failure time, a 5xx from the app's own backend, the same request fired twice, misbehaviour when the trace's steps are replayed at human speed in the paused session, a locator gone because the page shows an error or changed copy. Test: a strict-mode violation, a navigation between the action and its assertion, `waitForTimeout`, a missing await, an assertion on list order, a locator that matches zero or several elements in a transient state. Environment: a third-party timeout, a 403 or challenge, one runner or shard only, an action within five percent of its timeout across the runs. Data: a unique-constraint error under parallelism, a record another test changed, failures clustered at midnight or month end. The same failing line every run is deterministic; different lines mean shared state or ordering. One marker is unknown: report the candidate classes and the one probe that decides. Done when the entry has the class and both markers.

4. **Hypotheses and one change.** Three to five, ranked, each falsifiable as "if X is the cause, changing Y turns the loop green". Test the top one with one change per run; after three failed changes discard them and reclassify. A test cause is fixed at its source: a locator repaired in priority order, role and name, label, placeholder, text, test id, with old, new, the reason both resolve to the same element and the snapshot excerpt; a race by asserting the state the action needs; a wrong expected value at its origin in `src/data` or the element read before the action, never at the assertion; a collision with data unique per worker and teardown in the fixture; unordered data asserted as a set. A product cause leaves the test red and its assertion untouched. An environment or data cause stops here with the evidence. Done when one change is applied, or none with the reason.

5. **Prove.** Invoke `verify` on the changed test. An intermittent failure is proven by ten runs alone and ten in the suite with retries off. Verdict per test: fixed, still flaky, or order-dependent when alone is green and the suite is red. Done when the runs are in the entry.

6. **Bug.** For a product cause: title `<Area>: <observable symptom>`, one bug per report. Steps with preconditions and the account by variable name; expected from the criterion; actual with the trace path and the redacted excerpt; frequency out of ten; base URL and browser; what does not trigger it; a workaround when one exists; severity S1 unusable or data loss, S2 main flow broken without workaround, S3 workaround exists, S4 cosmetic; the red test that will verify the fix; for a backend bug the request and response pair. Done when every product entry has its bug.

7. **Quarantine.** Only a proven flake: mixed results over ten runs and the cause unfound after two rounds, never a product failure. The test gets the `@quarantine` tag and an annotation with owner, reason, candidate classes, failure rate, date and expiry, so the pull-request lane skips it and the nightly lane still runs it; the plan's Risks gets the line. It returns only when its cause is fixed and proven by the same ten runs. Done when the annotation and the risk line exist.

8. **Clean and report.** Remove every probe, pause and tagged log, `grep -rn 'DEBUG-'`, rerun the original reproduction once, and write `debug.md`: one entry per test, bugs, quarantined, the answer. A test diagnosed twice or a page repaired twice goes under Open as a design problem. Done when `debug.md` has every section of its template filled and one entry per failing test.
